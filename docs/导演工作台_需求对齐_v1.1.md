## 0 结论

> **把导演的三次决策（审核一 → 审核二 → 挑片）从"读 20 万字 Markdown、口头给意见、靠 Agent 记住"，变成"一个网页队列：每项都有证据、有范围、有版本、有签字"；并让 提交 → 进度 → 回片 → 归集 → 挑片 真正连通。**

核心不是"显示内容"，而是 **审核范围的可执行性**。"确认第一场≠整集通过""认可外貌≠所有换装通过""方向可以≠无限生成授权"——这三条现在只靠 Agent 自觉，工作台要让它变成**系统不让越界**。

### 1.1 三条直接影响设计的结论

1. **草稿 ≠ 定稿**：草稿只能判断构图、表演、口型、衔接；身份会漂、音量会跳。挑片必须分档，"采用草稿"要二次确认。
2. **时长有硬边界，而且比"最短 5 秒"更麻烦**：
   - 训练区间 124–362 帧，**124 帧 = 5.17 秒**，所以最短生成 5.17 秒，不是整 5 秒
   - 帧数只能落 **17n+5** 格点（步长 17 帧 ≈ 0.71 秒），所以生成结果几乎总比标注时长长
   - EP002 实测：标注 826 秒，**实际会生成 855 秒，多出 29 秒全部要在剪辑裁掉**；90 镜里 **77 镜**属于"生成超长"
   - 3 个 4 秒镜（吸附 107 帧 = 4.46 秒）落在训练下限以下——这是唯一一类"短到不能生成"的镜头
3. **横屏 R2V 未验证**：现有 R2V 实测全是 800×1056 竖屏，短剧要 16:9。批量前必须先试一条 1344×768 的 R2V。

## 3 三个不变量

- **A 带范围的签字**：单元 × 文件版本（哈希） × 覆盖到哪
- **B 创作通过与生成授权分开**：认可拍法 ≠ 批准烧卡
- **C 只追加不覆盖**：文件变了，旧批准转"待复核"

**不做**：不改创作文件、不做多人权限、不替导演做艺术判断、不宣称未验证的能力。

## 5 审核二：分镜 · 连戏 · 试做 · 提示词 · 批次授权

**分镜墙**（现状一眼可见：3/90 有提示词、89/90 参考图断链、0 张首帧图）

**机械检查**（自动，明确标注"不等于艺术判断"）：
参考图存在性（89 处断链）／镜号规范／台词逐字对齐（90 段 vs 148 句）／时长合规（3 个 4s 低于下限）／画幅 16:9（未验证）／场次覆盖／服装道具状态／提示词规范（`non_diegetic_music: N/A`、三段式、`<Picture n>` 对应）／版本漂移

**批次授权单**：

```
批次 BATCH-EP002-001
 范围    SC001 前五镜 01…03C      档位  草稿 turbo6
 候选    3 条/镜  共 15 条        预估  2370 帧 ≈ 34 分钟 GPU
 输入    分镜 sha256 / 提示词 sha256 / 参考图 3 张（已校验）

 停止    连续失败 3 次 / 达上限 / 手动

### 5.5.2 三套图片状态（流程文件要求分开存放）

`选定图 / 候选图 / 废弃图` 不能混。

| 状态 | 含义 | 能否被下游引用 |
|---|---|---|
| 选定 | 导演采用，登记编号 + 路径 + 版本 | **能**，且只能引用这一类 |
| 候选 | 可用未选 | 不能，只能看 |
| 废弃 | 已否决 | 不能，保留不删 |

**硬规则**：未选定图不能自动成为正式参考。89 处断链的根源就是"引用"与"采用"没打通——分镜引用了一个从未被正式采用的路径。

### 5.5.3 图片批次授权单

```

 每项    4 张候选，共 28 张

**建议先做"先出 1 张测时间"**：出图耗时没标定过，先跑一张拿到真实数字，再决定批次上限，比拍脑袋填稳妥。

### 5.5.4 出图顺序上的约束

1. **先定人物，再出分镜**：人物采用图没定时出分镜，等于把不确定的脸固化进 90 张首帧
2. **先出关键机位**：不是 90 镜一次铺开；流程文件要求优先对话正反打、重要动作、复杂多人场面
3. **九宫格是可选工具**：用已选定单张拼预览板，不反过来用九宫格当首帧输入

## 7 生成对接

**接口**（已在本机验证）：`GET /system_stats`｜`POST /upload/image`｜`POST /prompt`→prompt_id｜`GET /history/{id}`｜`GET /queue`｜`GET /view`｜`POST /interrupt`

R2V 图结构：`MiniMaxH3ReferenceToVideo` + `ref_images.ref_image_0…8` + `LoadImage`，提示词用 `<Picture 1..3>`——**与现有视频提示词.md 完全对得上**。

**三档**：草稿 turbo4/6（78/106s，定构图表演口型）｜定稿 base20（295s，出片）｜同 seed 对照（SSIM≈0.60–0.64，不可互相替代）

**提交前硬校验**：参考图存在可解码（现在会拦 89/90 镜）／时长在 124–362 帧或标"超界需裁"／宽高 32 倍数且 16:9 已验／提示词三段式与 `<Picture n>` 对应／批次六要素齐全

**队列**：SQLite WAL，关网页继续跑；重启 `health()` + 逐个 `status()` 对账；幂等键 `sha256(镜号+提示词哈希+参数+参考图哈希)`；重试分"网络/损坏可自动 ≤2"与"内容不满不自动重抽"；四项停止条件

**素材回传**：`/view` 下载 → `制作成果/候选/<场>/<镜>/TASK-ID.mp4`，ffprobe 读真实时长/分辨率/音轨 + 抽首帧缩略图 → `media/index.json`

**隔离原则**：联调期间真跑的 3–5 条标 `TEST`，落 `制作运行/devtest/`，**不进正式候选目录**，避免污染挑片。

### 7.6 帧数网格：工作台必须同时显示两个时长

| 标注（剪辑） | 生成帧数 | 生成秒数 | 余量 |
|---|---|---|---|
| 4s | 107 | 4.46s | ⚠ 低于训练下限 124 |
| 5s | 124 | 5.17s | +0.17s |
| 6s | 158 | 6.58s | +0.58s |
| 7s | 175 | 7.29s | +0.29s |
| 8s | 192 | 8.00s | 正好 |
| 9s | 226 | 9.42s | +0.42s |
| 10s | 243 | 10.12s | +0.12s |
| 11s | 277 | 11.54s | +0.54s |
| 12s | 294 | 12.25s | +0.25s |
| 13s | 328 | 13.67s | +0.67s |

**设计含义**：

1. 单镜页同时显示「剪辑 6s · 生成 158 帧 = 6.58s · 裁 0.58s」，不能只显示标注时长
2. **批次耗时按生成帧数算**，不能按标注时长算（5 镜示例：27 分钟 → 34 分钟）
3. 三个 4 秒镜只有两条路：**改写到 5s 以上**（推荐，生成 124 帧几乎不用裁）或按 124 帧生成后裁 1.17 秒（会切掉表演尾部）
4. 剪辑阶段要预留"每镜尾部多 0.1–0.7 秒"的余量，这本来对表演是好事
