## 0 结论

1. **主链路是真的，不是演示壳**：00–09 成果台账、SHA/依赖校验、场景/资产索引、H3 视频任务、按卡 ComfyUI、版本锁定、首帧接续、队列落盘与重启恢复，都有真实数据和真实运行痕迹（41 条生成结果、2 个实例、4 条在途任务）。
2. **但三个地基问题会让“真实”变成“不可信”**：确认接口必报 400（还先写了本地确认）；任务失败不会阻断依赖（A 失败仍记完成，B 会继续跑）；VRAM 采样每 8 秒拉起一次 torch（单次实测 12.5 秒），持续抢 GPU/CPU。
3. **页面都能开，但页头是错的**：页头“0 场 · 0 镜 · 0 分”、选集“无分集数据”，读的是已废弃的 `剧集/EP002` 四文档数据；真实项目是 8 场/6 镜/36 资产，04 大纲已规划 **135 集 / 261 场**。
4. **文档与代码已经分叉**：README 写 17 步、90 格分镜墙、审核一~四、36/41 项测试；实际是 19 步旧模型（UI 已不用）、8 个新页面、32 项测试。新 00–09 模型没有一份 tracked 的说明或验收标准。
5. **当前不是“再加功能”的阶段，而是“先把确认、任务状态、测试隔离修到可信”的阶段**。这三处不修，后面每加一个功能都会放大返工。

## 3 缺陷清单（按严重度）

> 复现均在 8790 只读环境完成；涉及写操作的，只在函数级/临时目录验证，未污染正式项目。行号以 `e35ac69` 为准。

### P0-1 成果确认接口必报 400，且已先写入本地确认

- **现象**：任意草稿点「确认」，UI toast“记录失败”；但 `制作运行/确认状态.json` 已经多了一条 confirmed。
- **复现**：
  1. 打开「待确认」→ 任一草稿（如 `05-正式剧本/screenplay-timing-audit-v001.md`）→ 点「确认」。
  2. 观察响应 400：`未知单元类型: artifact`；再刷新，`确认状态.json` 已有该路径的 SHA 记录。
  3. 函数级最小复现：`confirms.record(tmp,'x.md','confirm')` 成功后，`store.append(tmp,1,{'type':'artifact','id':'x.md'},'pass')` 抛 `ValueError`。
- **根因**：`server.py:1512-1532` 先 `confirms.record`，后 `store.append`；`store.py:17` 的 `UNIT_TYPES` 不含 `artifact`；两步无事务。
- **影响**：新模型的核心“确认门禁”反馈错误；更糟的是本地确认已生效，`/api/gen/submit` 的提示词门禁会被**静默打开**——用户以为失败，系统却放行。审计链也断了。

### P0-2 任务失败不阻断依赖，B 会在 A 失败后继续跑

- **现象**：`sched._run_one` 的 `finally` 无条件 `_done.add(id)`；`_execute` 又把异常全部吞掉置 failed。A 失败后，B 的就绪判断 `all(d in _done ...)` 为真，B 被派发。
- **复现**：
  ```python
  sched._done.clear(); sched._failed.clear()
  comfyctl._alive = lambda port: True
  sched._runners['A'] = lambda port: (_ for _ in ()).throw(RuntimeError('x'))
  sched._run_one({'id':'A','kind':'video'}, 0)
  # A in _done == True, A in _failed == False
  # all(d in _done or d not in _runners for d in ['A']) == True
  ```
- **根因**：`sched.py:199-214`、`sched.py:241-254`；`vjobs.py:885-889`。
- **影响**：接续镜会拿不到首帧或拿旧帧；commit `d1c8a57` 声明的“依赖失败则连带取消”并不成立。依赖被取消时只从 `_pending` 移除，`vjobs._jobs` 里仍是 `queued`，成为幽灵任务。

### P0-3 VRAM 采样每 8 秒拉起一次 torch + CUDA，持续抢 GPU/CPU

- **现象**：`comfywatch._sample_vram` 每 8 秒 `subprocess.run(H3_PY -c "import torch...")`，遍历 8 张卡 `mem_get_info`；实测同一条命令 **12.5 秒**，`_vram_busy` 只是同进程串行，等于持续拉起。
- **复现**：
  ```bash
  time CUDA_VISIBLE_DEVICES=7 /checkpoints/huxian/h3/env/bin/python -c "import torch; ..."
  # real 12.5s；ps 可见 mem_get_info 进程连续出现
  ```
- **根因**：`comfywatch.py:91-115`（`timeout=90`，`sleep(8)`）。
- **影响**：生成期间每 8 秒在 8 张卡上初始化 CUDA 上下文，CPU 8.8 秒/12 秒；卡 1–3 已 99% 占用，这种采样会加剧争用、拖慢出片，也可能触发显存不足。算力页的显存数字完全可以用一次 `nvidia-smi --query-gpu` 拿到，不需要 torch。

### P1-4 任务状态不一致：排队中的 B 显示“生成中”，顶栏说“队列空闲”

- **现象**（评估时真实批次）：
  - `vjobs.json`：B-1/B-2 `status=running`、`execStartedAt=null`；
  - `/api/backend`：同一任务 `waiting`（ComfyUI 队列）；
  - 生成台：B 显示“生成中”；
  - 顶栏：`队列空闲`（只统计图片任务）；
  - 卡 0/4：显示“可加载”，但同时 `ComfyUI run=1 / pend=1`。
- **复现**：提交 2 个单元 × 2 次（或看当前 12:44 批次），同时打开「生成台」和「算力」。
- **根因**：`vjobs.py:791-795` 派发即写 running；`reconcile` 只把 waiting 写进内存映射，不落盘；`server.statusBar` 只看 `imgjobs`；`gpus.probe` 的 state 是“容量”不是“执行中”。
- **影响**：导演无法判断到底在跑还是排队；重复提交/误停；ETA 失真。

### P1-5 `test_all.py` import server 会启动生产恢复线程，测试不隔离

- **现象**：`test_all.py:84` `import server`；`server.py:1908-1914` 在 import 时执行 `vjobs.resume(PROJECT)` 并启动 `_video_recovery_loop`。测试进程会读/写正式 `app/run/vjobs.json`，并可能向 ComfyUI 重新提交 `queued` 任务、认领/下载历史成片。
- **复现**：在 `vjobs.json` 里留一条 `queued` 任务，启动 8790 服务，再运行 `python3 app/test_all.py`；观察测试进程的 `[resume]` 和两个进程同时写 `vjobs.json`。
- **根因**：服务副作用放在模块顶层而不是 `main()`；`JOBS_FILE` 是进程全局、无单写者锁；`test_all` 还依赖 8790 已启动。
- **影响**：测试可能污染生产、重复提交、丢任务；不能进 CI。测试通过数因此也不可信。

### P1-6 页头/选集读废弃数据：显示“0 场 0 镜 / 无分集数据”

- **现象**：所有页面顶部 `0 场 · 0 镜 · 0.0 分 · 断链 0 处`，选集按钮“无分集数据”；实际 8 场/6 镜/36 资产。
- **复现**：打开任意页；对比 `/api/scenes` 的 8 场与 `/api/data` 的 `stats.scenes=0`。
- **根因**：`dataset.load` 读 `剧集/EP002/剧本.md`（不存在）返回空态；`loadEp` 把它当全局 `S`；`sEpSel` 用空 `D.episodes`。
- **影响**：第一眼就不可信；多集/全剧入口实际不可用。

### P1-7 `/api/gen/submit` 有 `force` 旁路，批次记录不绑定版本/参数

- **现象**：`server.py:1709` 允许 `body.force=true` 跳过提示词确认；批次记录只有 notes，无提示词文件/SHA、参考图、seed、分辨率、范围。
- **复现**：`POST /api/gen/submit`，body 带 `force:true` 和一个未确认的提示词版本；请求成功，不产生任何“强制放行”记录。
- **影响**：直接违反“确认是真实门禁”；出问题无法追溯“当时批的是哪版、哪些图、什么参数”。

### P1-8 本地确认不改变阶段状态，待确认列表会重复出现，且无法撤回

- **现象**：即使确认成功，`artifacts.build` 的阶段计数仍按登记表 `status`；`sPending` 只过滤 `status==='draft'`，不看 `local`。确认过的文件仍列在待确认，阶段仍显示“待确认”；已确认成果没有“退回/重确认”按钮。
- **复现**：确认任一草稿后刷新「待确认」/「工作流」。
- **影响**：导演会重复确认、误以为没生效；无法撤回误确认。

### P1-9 文件/媒体接口的前缀校验可被同名前缀目录绕过

- **现象**：`str(f).startswith(str(root))` 会把 `.../有谁共鸣2_audit` 当成项目内。
- **复现**：创建 `有谁共鸣2_audit/x.txt`，`GET /api/proj/text?p=../有谁共鸣2_audit/x.txt` 返回 200 和文件内容（本次已验证并清理）。
- **根因**：`server.py:1103`、`1124`、`1365`、`1668` 等处。

### P2-10 `/api/plan` 未定义 `batch_id`，必抛 NameError

## 4 架构评价（最多 5 条，按阻碍程度）

### 4.1 新旧两套模型并存，没有单一事实源

`server.py` 同时服务 00–09 阶段/成果（新）和 `剧集/EP002` 四文档 + 19 步工作流 + 审核一~四（旧）。页头、选集、导出、决策走旧模型，页面主体走新模型；`decisions.jsonl`（31 条）与 `确认状态.json`（5 条）又是两套。**阻碍**：任何“确认/授权/进度”都要先问“以哪套为准”；改一处很容易只改到死代码。建议先定一个模型（看起来应是 00–09 + 成果确认），把旧链路明确标记/移除。

### 4.2 import 即启动后台线程，进程全局状态无单写者

`server.py` 在模块顶层 `resume` + 起恢复线程；`vjobs.JOBS_FILE`、`sched` 的 `_pending/_done`、`imgjobs._jobs` 都是进程全局。测试一 import 就碰生产；两个进程同时写 `vjobs.json` 没有锁；图片任务重启即丢。**阻碍**：测试不可信、重启不可控、任务会丢/重。建议把副作用收进 `main()/start()`，任务队列落到项目 `制作运行/`，用 SQLite/文件锁做单写者。

### 4.3 任务状态机没有定义清楚

当前至少有 `queued / dispatched / waiting / running / done / failed / aborted / interrupted / cancelled / deleted` 十个字符串，但迁移规则分散在 `vjobs._execute`、`reconcile`、`sweep`、`sched._worker`、`server.backend_state` 五处；`running` 在派发时就写，失败又被当完成。**阻碍**：无法可靠回答“现在到哪一步/失败会不会连带/重启后谁会续跑”。建议先画状态机，所有迁移只走一个函数并落盘；依赖完成条件用 `succeeded` 而不是 `done`。

### 4.4 审批与授权账本分裂，且没有绑定 SHA/版本

`artifact-state.json` 管登记状态，`确认状态.json` 管本地确认，`decisions.jsonl` 管旧 gate 1/2/3；`/api/artifact/confirm` 想同时写两处但没有事务；`/api/gen/submit` 写批次记录却不含提示词版本/SHA/参考图/seed。**阻碍**：无法证明“这次生成用的是哪一版、谁批的、范围是什么”。建议做一份 append-only 审批账本：`approval_id + path + sha256 + version + scope + verdict + at`；提交任务引用 `approval_id`，没有有效 approval 不允许提交（去掉 force）。

### 4.5 GPU 编排在 Web 进程内，采样方式不可持续

ComfyUI 启停、调度、WS、VRAM 采样都在 `server` 进程；`_sample_vram` 每 8 秒拉起 12.5 秒的 torch 进程；服务重启会中断调度（ComfyUI 还在跑）。**阻碍**：生成期间的 UI/调度互相拖累；无法水平扩展；重启风险高。建议采样改用 `nvidia-smi`（毫秒级、不初始化 CUDA），调度器/恢复线程独立成 worker，Web 只读状态。
